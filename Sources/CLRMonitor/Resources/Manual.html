Quick start

  1. Open Options to show the sidebar.
  2. Select the MIDI input ports you want to observe. Use All next to Inputs to select or clear the listed inputs in one click.
  3. Switch Monitoring on. The switch turns green.
  4. Play your controller. The newest visible event appears above History. Click a history row to inspect it.
  5. Switch Monitoring off to stop capture. History stays visible under the red OFF overlay.

Output monitoring is optional. Input capture works without installing the output-monitor driver.

Inputs & outputs

Inputs

Inputs are CoreMIDI source ports: controllers, interfaces, or virtual sources created by software. Check a port to capture its incoming MIDI. Refresh scans for devices; the app also refreshes automatically.

Outputs

Outputs are CoreMIDI destinations. With the output-monitor driver installed and available, check a destination to observe MIDI that other apps send to it. This does not change the sending app’s routing.

Each list has its own All checkbox. Checked means every listed port is selected. If some are selected, clicking All selects the whole list; clicking again clears it. These controls apply to ports currently listed. Newly discovered ports are selected automatically. Individual exclusions are remembered during the current app session across reconnects when the device keeps the same unique ID.

Example: Ableton Live → Kenton Killamix. Select Kenton under Outputs. Events appear as OUT · Kenton Killamix. Kenton is the destination; this does not mean the controller generated those events.

The app lists exposed MIDI ports, not running applications. Some software names its virtual ports after itself; other apps do not expose a source port. CoreMIDI’s monitor callback does not identify the sending application, so output events cannot reliably be labeled “Ableton Live.”

Receive from software

This checkbox creates a virtual MIDI destination named CLR MIDI Monitor — Receive while Monitoring is on. Other apps can select it as their MIDI output to send messages directly to this monitor.

Unchecking it removes that virtual destination. It does not stop observation of other destinations selected under Outputs.

Send directly from Ableton Live

  1. In CLR MIDI Monitor, enable Receive from software and turn Monitoring on.
  2. In Live’s Settings → Link, Tempo & MIDI, enable Track for the output CLR MIDI Monitor — Receive.
  3. On the MIDI track, select MIDI To → CLR MIDI Monitor — Receive and the desired channel.
  4. Play the MIDI clip. Directly received messages appear as VIRTUAL · CLR Receive.

Choosing this destination instead of Kenton redirects that track to the monitor. To keep sending to Kenton, leave Live’s routing unchanged and observe Kenton under Outputs instead.

You do not need the output-monitor driver for this direct-receive method.

Output monitor setup

  1. Choose a quiet time and close MIDI-dependent apps before the first installation.
  2. Below Receive from software, click Install Output Monitor.
  3. The app installs the driver bundled inside it into your account’s ~/Library/Audio/MIDI Drivers/ folder. There is no separate download.
  4. The install button and explanation disappear once installation is detected. Check the status under Outputs.

Installation does not force a CoreMIDI restart. If the status remains Installed · waiting for CoreMIDI, reopen your MIDI apps when convenient. If it remains unavailable, restart the Mac after saving your work.

StatusMeaning
Output monitor not installedInput and direct virtual reception work; destination spying needs the bundled driver.
Installed · waiting for CoreMIDIThe plugin is present, but the running MIDI server has not exposed it to this app yet.
Driver available · idleThe driver is reachable; Monitoring is off or no outputs are selected.
Output monitoring activeThe app has an active subscription for selected destinations.
Driver in use by another monitorAnother app instance owns the subscription. Turn monitoring off in that instance or quit it, then allow a few seconds.
Connection/response unavailableOutput observation is not working. Input capture is independent. Save work before restarting MIDI apps or the Mac.

Remove the driver

Quit MIDI apps. In Finder, choose Go → Go to Folder… and enter ~/Library/Audio/MIDI Drivers/. Move only CLR Output Monitor.plugin to a folder outside MIDI Drivers, or to Trash. Leave other vendors’ plugins alone. Already-loaded driver code remains in memory until CoreMIDI next restarts; restart the Mac at a convenient time. The source distribution also includes scripts/output-driver.sh uninstall, which archives the CLR plugin outside the discovery folder.

Reading events

The highlighted Last Observed Event row shows the latest event that passes the current display filters. History uses the same fields and retains up to 10,000 events.

FieldMeaning
TimeLocal arrival time recorded by the monitor. This is not a measurement of hardware latency.
PathIN: input source; OUT: observed destination traffic; VIRTUAL: sent directly to CLR Receive.
PortThe source or destination associated with the event.
MessageDecoded type, such as Note On, Control Change, Clock or Pitch Bend.
ChMIDI channel, 1–16 where applicable. A dash means no channel is associated with that message.
Note / ControllerThe note or controller, using the selected name/number format.
ValueThe decoded message value, such as velocity or controller value.

Inspect

Click a history row to open its details in the Inspect card below the list. It includes port, group/channel, data, the original CoreMIDI timestamp and Raw UMP. UMP means Universal MIDI Packet; raw words are shown in hexadecimal and remain unchanged by display formatting. Copy raw copies those words. Right-click a history row and choose Copy event to copy a readable summary.

A MIDI timestamp of zero means the sender did not supply a scheduled timestamp. Events may have been scheduled ahead; observed arrival is not a guarantee of when hardware physically played them.

Counters and Clear

Captured counts retained events; shown counts events passing display filters. Dropped reports copies the monitor could not retain because of overload, contention or oversized packets. Aged out counts old events removed at the history limit. A monitor drop is not itself proof that MIDI delivery to the destination failed.

Clear removes retained history and resets the counters. Export first if you need to keep it.

Display & filters

Controller Format selects controller names or decimal numbers. Note Format selects note names or decimal numbers. Middle C chooses C3 or C4 naming and is disabled in decimal-note mode. These preferences apply to retained data immediately and are remembered between launches.

Display filters enables or bypasses all the controls below. Filters affect the latest row and history, not the underlying capture.

  • Hide Voice Messages: notes, poly pressure, control/program changes, channel pressure and pitch bend.
  • Hide System Common: time-code quarter frames, song position, song select and tune request.
  • Hide SysEx: System Exclusive data, including fragments.
  • Hide Clock: MIDI timing-clock events.
  • Hide Active Sensing: active-sensing events.
  • Search: matches port names, message types, formatted data, details and raw hexadecimal words.

Start, Continue, Stop and Reset are real-time messages; Hide System Common does not hide them. Inspect can retain the selected event even if a display filter later hides its row.

Click the icon or Options text to hide/show the sidebar. Its visibility is remembered.

Export, File menu & windows

Choose File → Export Capture… (⇧⌘E) or click Export in the header. Choose a filename and location to write a JSON file. Export includes the entire retained capture, including events hidden by display filters, timestamps, port information and raw words. It is disabled when history is empty.

Capture is held in memory. Export before quitting if you need a permanent copy. Version 1.0 does not reopen exported captures or save a document-style session. Events older than the retention limit are not included.

File → New Window opens another view of the same capture session. All windows share monitoring, port selections, filters and history. Export from any window saves the same retained session. Additional windows add display work; one window is the simplest choice for a busy live setup. Separate app processes are different: only one can own the output-driver subscription at a time.

Choose Help → CLR MIDI Monitor Help to reopen this guide. It is bundled with the app and works offline.

Troubleshooting

A newly connected controller is missing

Click Refresh. Check the controller’s cable, power and MIDI availability in macOS. The app can only list ports exposed through CoreMIDI. Make sure the correct input is checked.

No events are visible

Check that Monitoring is on and the correct ports are selected. Temporarily switch Display filters off. For direct software reception, confirm the virtual destination is enabled and selected in the sending app. For output spying, check the driver status.

OUT Kenton continues after Receive from software is unchecked

That checkbox controls only CLR’s virtual receive destination. Uncheck Kenton under Outputs to stop observing Live → Kenton. This leaves Live’s routing and delivery untouched. Old history rows remain visible.

I see a port name but not Ableton Live

Output events identify destinations, not the sending app. A software name appears only when the software exposes a MIDI port with that name.

Two entries look like the same message

A message may be observed at different points—for example, an input and an output. Compare Path and Port. Two observations are not evidence that the monitor retransmitted the message.

The app feels busy or reports drops

Select fewer ports, close additional monitor windows and clear unneeded history after exporting. Display filters improve readability but do not reduce the amount captured. Heavy traffic can exceed the monitor’s finite capacity; the app does not block MIDI delivery to wait for its display.

Limits & safety

  • The app observes MIDI; it does not send, forward, echo or create MIDI-thru routes. It therefore does not construct a MIDI feedback loop. Existing routes created by other software are outside its control.
  • Monitoring still consumes CPU and memory. There is no guarantee of zero overhead or perfect operation with every driver and device.
  • The output driver copies selected traffic through bounded queues. It expires subscriptions after approximately three seconds without a polling client and never restarts CoreMIDI automatically.
  • MIDI kept entirely inside a DAW, instrument or plugin may never pass through CoreMIDI and cannot be observed here.
  • MIDI 1.0 decoding is supported. MIDI 2.0 semantic decoding and SysEx reassembly are not complete; unsupported data remains visible as raw UMP/fragments. The input API requests MIDI 1.0, so CoreMIDI may convert newer data before delivery.
  • This release targets Apple Silicon Macs with macOS 13 or later. No Intel binary is included.
